Участник делает ревью PR #$0. Ревью — его работа и его мнение: ты помогаешь разобраться и сформулировать, но решение «одобрить» или «попросить правки» принимает он.

1. **Прочитай PR:** `gh pr view $0 --comments` и `gh pr diff $0`. Найди связанную задачу (`Closes #N`) и прочитай её: `gh issue view N`.
2. **Объясни участнику PR простыми словами:** что меняется, зачем, какие файлы. Это полезно и для защиты — на ней спрашивают про чужие части.
3. **Сверь по списку** и для каждого пункта скажи «да» или «нет, потому что…»:
   - выполнены все пункты «Готово, если» из задачи;
   - файлы лежат там, где велит `docs/architecture.md`, правила зависимостей соблюдены;
   - есть тесты там, где они нужны, и в PR написано, как проверить;
   - ответы и ошибки соответствуют `docs/api.md` и разделу «Ответы и ошибки» в `docs/architecture.md`;
   - в наборах: обязательные поля есть, `id` уникальны и не изменены у опубликованных карточек, источники указаны, башкирские буквы не заменены похожими латинскими. Переводы не оценивай — это решает контент-лид;
   - нет секретов, лишних файлов, закомментированного мусора;
   - раздел «Использование ИИ» заполнен по существу, а не «использовал для кода».
4. **Проверить руками (по желанию участника):** `gh pr checkout $0`, затем `./gradlew test` и `./gradlew :server:run` с проверкой ответа в браузере. Перед этим проверь `git status`: если у участника есть свои незакоммиченные изменения, сначала предупреди.
5. **Подготовь замечания:** каждое — где (файл и строка), что не так, почему это важно, как можно исправить. Тон доброжелательный, без «неправильно» и «плохо». Отдельно отметь, что сделано хорошо.
6. **Покажи итог** и предложи вариант: одобрить (`gh pr review $0 --approve --body "…"`), попросить правки (`gh pr review $0 --request-changes --body "…"`) или оставить комментарий (`gh pr review $0 --comment --body "…"`). Выполняй команду только после явного «да» участника и с текстом, который он одобрил.

Не одобряй PR, если участник сам не понял, что в нём сделано: сначала разберитесь.
