Помоги участнику аккуратно сдать задачу. На GitHub автоматические проверки отключены, поэтому эта команда и есть проверка перед ревью. Каждый шаг, который что-то отправляет на GitHub или меняет историю, выполняй только после его «да».

1. **Где мы:** `git branch --show-current`. Если это `main` — остановись: работа должна быть в ветке задачи. Номер задачи возьми из имени ветки (`feature/12-…` → #12).
2. **Что изменилось:** `git status` и `git diff main...HEAD --stat`, плюс незакоммиченное. Коротко перескажи изменения. Если в изменениях есть файлы, не относящиеся к задаче, спроси, нужны ли они.
3. **Свежий main.** `git fetch origin`, затем предложи `git merge origin/main`. Если есть конфликты — покажи их по одному, объясни, откуда каждый (чья правка), и реши вместе с участником. Не выбирай «свою» или «чужую» версию молча.
4. **Архитектура.** Сверь пути новых файлов с `docs/architecture.md`. Проверь правила: `domain/` не импортирует `io.ktor` и `java.io`; DTO только в `api/`; ошибки отдаются JSON с правильным кодом. Нарушения покажи и предложи исправить до PR.
5. **Проверки** из раздела «Проверка перед PR» в `CLAUDE.md`: `./gradlew test` (если код сервера уже есть). Изменились файлы в `content/` — проверь каждый: JSON открывается, обязательные поля на месте, `id` уникальны, у опубликованных карточек `id` не изменились, `sources` заполнены. Переводы не оценивай и не меняй. Тесты падают — сначала разберитесь, PR не открываем. Если менялось API, напомни приложить к PR пример ответа и обновить `docs/api.md`.
6. **Секреты.** Убедись, что в изменениях нет `.env`, `local.properties`, ключей, токенов и паролей. Нашёл — остановись и скажи.
7. **Коммит.** Предложи сообщение на русском в формате `#<номер>: что сделано` (например `#1: GET /sets читает наборы из content`). После согласия — `git add` нужных файлов и `git commit`.
8. **Отправка:** `git push` (при первой отправке — `git push -u origin <ветка>`).
9. **Текст PR** по `.github/pull_request_template.md`:
   - «Что сделано» — по сути, с `Closes #<номер>`;
   - «Как проверить» — конкретные шаги и команды;
   - «Использование ИИ» — набросай черновик по этой сессии (для чего использовали Claude, какие были ключевые запросы), но пункты «Что проверил(а) сам(а)» и «Где решил(а) иначе» **попроси участника заполнить самому**. Не выдумывай за него;
   - чек-лист отметь только то, что действительно сделано в шагах 4–6.
   Покажи текст, дождись правок и согласия.
10. **Открой PR:** `gh pr create --base main --title "#<номер>: <как в коммите>" --body-file <временный файл> --reviewer Mimir-tu`. Если участник хочет второго ревьюера из своей команды, добавь его логин через запятую. Если `gh` недоступен — дай ссылку на создание PR из вывода `git push` и текст для вставки.
11. **Напомни** перенести карточку в «На ревью». Когда придут замечания — команда `/fix-review`.
