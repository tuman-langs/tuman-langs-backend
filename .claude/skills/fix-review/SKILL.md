name: fix-review
description: Разобрать замечания ревьюера к своему pull request, исправить их в той же ветке и отправить обновление. Вызывается командой /fix-review.
disable-model-invocation: true
allowed-tools: Bash(git status *) Bash(git diff *) Bash(git log *) Bash(git branch *) Bash(git fetch *) Bash(gh pr view *) Bash(gh pr diff *) Bash(gh api repos/*) Bash(./gradlew test) Bash(./gradlew test *)

Участник получил замечания к своему PR. Помоги ему понять каждое и исправить. Отправку на GitHub делай только после его «да».

1. **Найди PR текущей ветки:** `git branch --show-current`, затем `gh pr view --comments`. Замечания к строкам кода: `gh api repos/{owner}/{repo}/pulls/<номер>/comments --jq '.[] | {path, line, body, user: .user.login}'`.
2. **Составь список замечаний** таблицей: № — файл и строка — что просят — как поняли — что будем делать. Если замечание непонятно или участник не согласен — предложи вежливый ответ ревьюеру с вопросом или аргументом, а не исправляй молча.
3. **План правок** покажи и дождись согласия.
4. **Исправь** по одному замечанию, после каждого коротко объясни, что изменилось и почему так лучше. Участник должен уметь объяснить правку сам.
5. **Проверки:** `./gradlew test`, а для наборов — проверка структуры JSON как в `/finish-task`. Падают — сначала чиним.
6. **Коммит:** `#<номер задачи>: правки по ревью — <коротко>`, затем `git push` в ту же ветку. Новый PR не нужен: открытый обновится сам.
7. **Ответы ревьюеру:** предложи короткий ответ на каждое замечание («исправлено в <коммит>» или аргумент). Опубликовать общий комментарий можно командой `gh pr comment <номер> --body "…"` — только после «да». Отметить обсуждения решёнными («Resolve conversation») участник может сам на странице PR.
8. **Напомни:** после новых коммитов одобрение сбрасывается, ревьюер посмотрит ещё раз. Карточка остаётся в «На ревью».
