Участник начинает задачу #$0. Помоги ему начать правильно и ничего не пиши в код, пока он не согласует план.

1. **Прочитай задачу:** `gh issue view $0 --comments`. Если `gh` не установлен или не авторизован, попроси вставить текст задачи и подскажи `gh auth login`. Если такого issue нет в этом репозитории, проверь второй: `gh issue view $0 --repo tuman-langs/tuman-langs-backend` (или `tuman-langs-mobile`) и скажи, в какой папке нужно работать.
2. **Проверь задачу.** Есть ли ответственный, сроки, этап ТЗ и проверяемый критерий «Готово, если»? Если ответственный — не текущий пользователь (`gh api user --jq .login`), предупреди и спроси, точно ли продолжать. Если критерия нет — предложи сформулировать его и написать руководителю в комментарии к issue.
3. **Проверь зависимости — до создания ветки.** Участник должен сразу узнать, если его задача заблокирована.
   - Связи на GitHub: `gh api repos/{owner}/{repo}/issues/$0/dependencies/blocked_by --jq '.[] | {number, title, state, url: .html_url}'` (если задача из другого репозитория — подставь его).
   - Раздел «## Зависимости» в тексте задачи. Для каждой ссылки вида `tuman-langs/<репозиторий>#N` выполни `gh issue view N --repo tuman-langs/<репозиторий> --json state,title,assignees,comments`.
   - 🚧 **Блокер** снят, если связанная задача закрыта или выполнено условие «Снят, когда…» (проверь комментарии). Не снят — **начни ответ с блока «🚧 Блокер»**: какая задача, кто ответственный, что должно случиться. Предложи, что делать прямо сейчас (часть «До этого: …»), и не пиши код для заблокированной части.
   - 🤝 **Договорённость** — найди итог в комментариях задачи, где он должен появиться (поля, формат, «ок»). Итога нет — предупреди «🤝 Нужно договориться»: с кем, о чём, до какой даты; если дата прошла — скажи прямо. Предложи короткий черновик комментария или сообщения этому человеку; опубликовать через `gh issue comment` — только после «да» участника. Начинать работу можно с заглушки — отметь это в плане.
   - ➡️ **От тебя ждут** — напомни, кому и к какому сроку нужен результат.
   - Зависимостей нет или все сняты — одной строкой «✅ Блокеров нет».
4. **Проверь рабочую копию:** `git status`. Есть незакоммиченные изменения — остановись и спроси, что с ними делать. Ничего не удаляй сам.
5. **Обнови main:** `git switch main`, `git pull`.
6. **Ветка.** Если ветка для этой задачи уже есть (`git branch -a --list "*/$0-*"`), переключись на неё. Иначе придумай имя по правилу `<тип>/<номер>-<2–4 английских слова через дефис>`:
   - тип по метке issue: `feature` → `feature`, `bug` → `fix`, `test` → `test`, `docs` или `research` → `docs`, `content` → `content`, `design` → `design`, остальное → `feature`;
   - пример: `feature/12-card-editor`, `fix/31-streak-reset`.
   Покажи имя и, когда участник согласится, создай ветку, привязанную к issue: `gh issue develop $0 --name <имя> --checkout`. Если команда недоступна — `git switch -c <имя>`, затем `git push -u origin <имя>`.
7. **Напомни** перенести карточку на доске в колонку «В работе» (https://github.com/orgs/tuman-langs/projects/1).
8. **Прочитай контекст:** `docs/architecture.md` (куда класть файлы), `docs/api.md` и `content/README.md`. ТЗ и команда лежат в репозитории mobile: если он склонирован рядом — `../tuman-langs-mobile/docs/tz.md` и `docs/team.md`, иначе `gh api repos/tuman-langs/tuman-langs-mobile/contents/docs/tz.md --jq .content | base64 -d` или попроси участника открыть их на GitHub.
9. **План.** Составь план и покажи его в таком виде:
   - **Зачем:** какое требование ТЗ закрываем, одной фразой;
   - **Файлы:** список путей по `docs/architecture.md` с пометкой «новый» или «изменить» и одной строкой, что в нём будет;
   - **Чужие зоны:** если нужно менять файлы из зоны другого участника (например `content/` у Богданова Е. или `server/` у Василенко А.), так и напиши и предложи сначала договориться с ним в комментарии к задаче;
   - **Проверка:** какие тесты напишем и как проверим руками (запрос к серверу в браузере или `curl`);
   - **Что понять:** 2–3 понятия, которые участник должен разобрать, чтобы защитить работу (например «что такое маршрут Ktor»).
   Объясни простыми словами: участник первокурсник. Дождись согласия, прежде чем менять код.
10. **Работай маленькими шагами.** После каждого заметного шага (запрос отвечает, тест проходит) предложи коммит `#$0: что сделано` и коротко объясни, что изменилось.

Если задача выходит за рамки MVP из `CLAUDE.md`, противоречит ТЗ или `docs/architecture.md` — скажи об этом и предложи обсудить с руководителем, а не делай молча.
