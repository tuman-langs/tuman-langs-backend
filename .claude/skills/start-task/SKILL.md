Участник начинает задачу #$0. Помоги ему начать правильно и ничего не пиши в код, пока он не согласует план.

1. **Прочитай задачу:** `gh issue view $0 --comments`. Если `gh` не установлен или не авторизован, попроси вставить текст задачи и подскажи `gh auth login`.
2. **Проверь задачу.** Есть ли ответственный, сроки, этап ТЗ и проверяемый критерий «Готово, если»? Если ответственный — не текущий пользователь (`gh api user --jq .login`), предупреди и спроси, точно ли продолжать. Если критерия нет — предложи сформулировать его и написать руководителю в комментарии к issue.
3. **Проверь рабочую копию:** `git status`. Есть незакоммиченные изменения — остановись и спроси, что с ними делать. Ничего не удаляй сам.
4. **Обнови main:** `git switch main`, `git pull`.
5. **Ветка.** Если ветка для этой задачи уже есть (`git branch -a --list "*/$0-*"`), переключись на неё. Иначе придумай имя по правилу `<тип>/<номер>-<2–4 английских слова через дефис>`:
   - тип по метке issue: `feature` → `feature`, `bug` → `fix`, `test` → `test`, `docs` или `research` → `docs`, `content` → `content`, `design` → `design`, остальное → `feature`;
   - пример: `feature/12-card-editor`, `fix/31-streak-reset`.
   Покажи имя и, когда участник согласится, создай ветку, привязанную к issue: `gh issue develop $0 --name <имя> --checkout`. Если команда недоступна — `git switch -c <имя>`, затем `git push -u origin <имя>`.
6. **Напомни** перенести карточку на доске в колонку «В работе».
7. **План.** Найди в ТЗ (`docs/tz.md` репозитория tuman-langs-mobile; если его нет рядом — спроси участника или руководителя) требование, к которому относится задача, и составь план: какие файлы затронем, что проверим (тест, запуск на устройстве), что участнику нужно понять или изучить. Объясни простыми словами — участник первокурсник и должен уметь защитить эту работу. Дождись согласия, прежде чем менять код.

Если задача выходит за рамки MVP из `CLAUDE.md` или противоречит ТЗ — скажи об этом и предложи обсудить с руководителем, а не делай молча.
